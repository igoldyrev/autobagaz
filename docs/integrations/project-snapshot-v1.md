# Autobagaz Project Snapshot API v1

Контракт описывает read-only снимок состояния проекта «Автобагаж» для внешнего
сборщика данных. Текущая версия схемы — `1.0`, идентификатор источника — `autobagaz`.

## Запрос

```http
GET /internal/monitoring/project-snapshot?date=2026-10-02&limit=3
Authorization: Bearer <DAILY_BRIEF_MONITORING_TOKEN>
Accept: application/json
```

Параметры:

- `date` — необязательная дата отчёта в формате `YYYY-MM-DD`; по умолчанию текущая
  дата в `app.display_timezone`;
- `limit` — необязательное количество последних изменений для каждого
  администратора и общего списка, целое число от 1 до 10; по умолчанию 3.

Ответы не кешируются: `Cache-Control: no-store, private`.

Коды ответа:

- `200` — снимок сформирован;
- `401` — Bearer-токен отсутствует или неверен;
- `422` — параметры запроса не прошли валидацию;
- `503` — `DAILY_BRIEF_MONITORING_TOKEN` не настроен на сервере;
- `429` — превышено ограничение 30 запросов в минуту.

## Схема ответа

Машиночитаемая JSON Schema находится в
[`autobagaz-project-snapshot-v1.schema.json`](autobagaz-project-snapshot-v1.schema.json).

Основные правила:

- время `generated_at` и границы `period` передаются в ISO 8601;
- время входа, присутствия и изменений администраторов нормализовано в UTC;
- денежные суммы передаются строкой с двумя знаками после точки, чтобы не терять
  точность при десериализации;
- `orders.by_status` всегда содержит все пять известных статусов, даже когда их
  значения равны нулю;
- `created_for_day` и `activity` рассчитываются для указанного `period`;
- `callback_requests`, `products` и `vehicle_configurations` отражают состояние на
  момент формирования снимка;
- персональные данные покупателей, состав заказов и исходные комментарии в ответ
  не включаются;
- изменения отображаются только для разрешённых безопасных типов объектов.

## Состояние уведомлений

Поле `notifications` отражает текущее состояние доставки email,
независимо от запрошенной даты отчёта:

```json
"notifications": {
  "pending": 0,
  "queued": 0,
  "failed_notifications": 0,
  "overdue": 0,
  "failed_jobs": 0
}
```

`pending` — ещё не поставленные задания, `queued` — поставленные и не завершённые,
`failed_notifications` — уведомления с исчерпанными попытками, `overdue` — все
неотправленные уведомления старше 15 минут. `failed_jobs` — число всех неудачных
заданий приложения; при другом драйвере хранения ошибок вместо `database-uuids`
значение равно `null`. Счётчики могут пересекаться.

Если `failed_notifications`, `overdue` или `failed_jobs` больше нуля либо
`scheduled_tasks.state` равно `degraded`, верхнее поле `state` равно `degraded`;
иначе — `ok`. HTTP-код сформированного снимка
остаётся 200. При недоступной БД запрос завершается ошибкой; внешний монитор
должен также обрабатывать HTTP-ошибки и таймауты.

Внешний сборщик должен проверять endpoint каждые пять минут, уведомлять при
переходе в проблемное состояние и восстановлении, не повторять одинаковые
оповещения. Добавление полей на стороне API не настраивает внешний сборщик
автоматически. В API нет адресов получателей, токенов и текстов исключений.
Информация о заказах остаётся в `orders`: количество и суммы по статусам,
новые за выбранный день и ожидающие обработки.

## Счётчики серверных ошибок

`site_errors` содержит `groups`, `occurrences` и `last_at` (ISO 8601 или `null`).
Это агрегаты сохранённых групп исключений и HTTP-ответов 5xx Laravel с активностью за последние
сутки. Хранилище ограничено 100 группами. Счётчик группы накапливается с первого
сохранённого события, поэтому `occurrences` не является точным числом ошибок
за скользящие 24 часа. Тексты исключений, stack trace и данные запросов в API
не передаются. Сбор работает и без настроенного Telegram. Очистка файлового
кеша сбрасывает счётчики; внешний сборщик не должен считать отсутствие событий
доказательством исправления ошибки. Поле `state` определяется состоянием
уведомлений и выполнения задач; эти счётчики отражают историю исключений, а не текущую доступность.

## Выполнение задач и успешные отправки

`scheduled_tasks` содержит `state` (`ok` или `degraded`) и объект `tasks`:

- `scheduler` — отметка задачи Scheduler каждую минуту, порог 180 секунд;
- `dispatch_notifications` — успешное завершение `orders:dispatch-notifications`,
  порог 180 секунд; при оставшихся ожидающих записях отметка не обновляется;
- `notification_monitor` — успешное завершение `telegram:monitor-notifications`,
  порог 900 секунд. Если Telegram отключён, успешное выполнение не доказывает
  доступность Telegram: проверка отправки в этом случае пропускается.

Каждая задача содержит `last_succeeded_at` (UTC ISO 8601 или `null`),
`max_age_seconds` и `state`: `ok`, `stale` (возраст не меньше порога) либо
`never` (нет успешных запусков). `never` и `stale` дают `degraded`.
Отметки сохраняются в таблице `monitoring_heartbeats`, не зависят от очистки
кеша и не обновляются при чтении отчёта. Ручной успешный запуск команды также
обновляет её отметку; отметка `scheduler` обновляется только Scheduler.
После первой установки до выполнения задач ожидается состояние `degraded`.
Эти отметки не доказывают работу worker: его сбои проявляются задержкой очереди.

`delivery.last_sent_at` — последняя успешная отправка любого уведомления за всё
время (UTC ISO 8601 или `null`). `delivery.sent_for_day` содержит счётчики за
запрошенный `period`: `total`, `order_created` (письма менеджерам о заказах),
`order_confirmation` (подтверждения покупателям), `callback_requested`
(письма о заявках на звонок). Это количество писем, а не уникальных заказов:
несколько менеджеров получают отдельные письма. Успех означает принятие письма
настроенным транспортом, а не подтверждение доставки в почтовый ящик.
Повторные снимки не суммируются; текущие счётчики заменяют предыдущие за тот же день.

Сборщик отдельно сохраняет время попытки, последнего успешного получения и
`generated_at` источника. Неудачный запрос не должен затирать последний корректный
снимок. Устаревшие данные нельзя показывать как текущее подтверждение исправности.
Оповещения о потере связи и восстановлении формируются сборщиком. Для полной
остановки общего хостинга необходим монитор вне этого хостинга.

## Совместимость

В пределах версии `1.x` существующие поля не удаляются и не меняют тип. Новые поля
могут добавляться, поэтому клиент должен игнорировать неизвестные свойства. Удаление,
переименование или изменение типа поля требует новой major-версии контракта и нового
маршрута либо согласованного периода миграции.

Старый маршрут `GET /internal/daily-brief/admin-activity` временно возвращает тот же
ответ для обратной совместимости. Новые клиенты должны использовать
`/internal/monitoring/project-snapshot`.
