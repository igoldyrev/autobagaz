## SQL на хостинге

Запросы выполнены через настоящий HTTP Kernel Laravel на Jino с актуальной
MariaDB 10.11.19. На каждом из шести маршрутов получены три ответа HTTP 200.
Кеш для диагностического процесса заменён изолированным ArrayStore: первый
запрос показывает пересчёт, два следующих — работу с прогретым кешем.
Рабочий общий кеш не очищался. Созданные анонимные сессии удалялись.

### Подтверждённые места для оптимизации

1. На подборе конфигурации 7 выполняются 92 отдельных `SUM(quantity)` по
   `order_reservations`, в том числе 46 лишних повторов одного расчёта.
   Это происходит и с прогретым кешем. В совокупности там 48 лишних точных
   повторов SQL; у конфигурации 1 — 35. Одинаковость проверялась по SQL и
   подготовленным драйвером значениям параметров, без публикации значений.
   `Product::getAvailableStockAttribute()` выполняет отдельный SUM, если не
   загружен `reserved_stock`. В `VehicleFitmentController` четыре списка
   товаров загружаются без существующего `withAvailability()`. Следующий шаг —
   использовать этот механизм для пакетной загрузки актуальных резервов.
2. Холодный пересчёт конфигурации 7 выполняет 44 отдельных проверки
   `compatibility_overrides` для базовых товаров. Нужна пакетная загрузка
   применимых исключений с сохранением действующих приоритетов и сроков.

Оптимизация обоснована количеством запросов и ростом нагрузки при расширении
каталога. Измеренные времена PHP пока составляют десятки/сотни миллисекунд;
измерений недостаточно, чтобы объявлять нехватку ресурсов хостинга.

## Контролируемая медленная сеть

Доступный браузер не предоставляет штатного ограничения сети. Для повторяемого
измерения использован временный локальный обратный прокси, который получает
реальные HTML и ресурсы опубликованного сайта по HTTPS. Все запросы к сайту
и Google Fonts идут через него; общий канал ответов ограничен 200000 байт/с
(1,6 Мбит/с), к каждому ответу добавлено 150 мс задержки. Оригинальные файлы
и настройки сети хостинга не менялись.

Браузер — 1280×720, браузерный кеш отключён заголовком `no-store`.
Для каждого маршрута выполнены один контрольный прогон без искусственного
ограничения и два прогона с ограничением. Локальный диагностический скрипт
собирал Navigation/Paint Timing, LCP, CLS и Resource Timing, показывал результат
в отдельной панели и передавал его только на локальный сервер. Панель и скрипт
не публиковались на сайте. Этот стенд добавляет собственные накладные расходы:
результаты являются контролируемой моделью, а не прямым прогоном DevTools,
полевой статистикой посетителей или приёмкой на физическом телефоне.

| Страница | LCP без ограничения, с | LCP на медленной сети, с | Load на медленной сети, с |
| --- | ---: | ---: | ---: |
| Автобагажники | 1,50 | 2,71–2,72 | 15,53–17,13 |
| Подбор, конфигурация 7 | 1,51 | 2,25–2,98 | 5,69–6,68 |
| LUX ТРЭК-1 | 1,49 | 2,08–2,14 | 4,56–4,63 |

LCP показывает появление крупнейшего видимого содержимого, Load — завершение
загрузки документа и зависимых ресурсов по событию браузера. При получении
результатов все изображения в видимой области загружены, горизонтального
переполнения не было. Для уверенного вывода о типичном времени посетителей
нужны более широкие измерения; два повтора показывают наблюдаемый диапазон.

У каталога получены 118–119 ресурсных запросов и около 1,46 МБ ресурсов без
основного HTML. Из них 87 логотипов марок занимают 1 058 260 байт, восемь
шрифтов — 258 408 байт, а 12 фотографий товаров — только 46 634 байта.
В шаблоне уже есть `loading="lazy"`, но в этом прогоне были загружены все 87
логотипов, включая марки вне раскрытого списка. Следующая задача — уменьшить
логотипы и исключить преждевременную загрузку скрытых марок; затем проверить
нужные начертания шрифтов. После изменений повторить тот же профиль.

## Реальные письма через SMTP и очередь

Созданы два явно диагностических заказа с нулевой суммой и одной служебной
позицией без товара. Складских резервов и платёжных операций у них нет.
Через `OrderWorkflow` выполнены переходы, создающие четыре разных события:
подтверждение менеджером, отмена, готовность к отправке и отправка.
Начальные письма о новой заявке менеджерам не создавались. Единственный
получатель четырёх статусных писем — согласованный пользователем адрес Яндекса.

Перед отправкой проверены настоящие `MAIL_MAILER=smtp` и очередь `database`.
Уведомления 34–37 поставлены в очередь в 19:43:16. Без ручного запуска worker
штатный минутный cron обработал их в 19:44:03–19:44:04; все получили `sent_at`,
ошибок и failed jobs нет. Постоянные SMTP-настройки не менялись.

Проверены заголовки четырёх писем, нужный снимок события, диагностическое
пояснение, отсутствие подтверждения оплаты и ссылки на актуальный заказ.
Обе защищённые ссылки через HTTP вернули 200 и показали диагностическую позицию.
Секретные ссылки, токены и учётные данные в отчёт не включены.

Пользователь подтвердил: **все четыре письма получены во входящих**.
Это подтверждение доставки в ящик дополняет серверные отметки принятия SMTP.

После подтверждения в 19:51:19 удалены только диагностические заказы 24–25,
их позиции, четыре отправленных уведомления и записи истории. В тестовых
письмах заранее указано, что диагностическая запись может быть удалена;
после очистки её ссылки перестают открывать заказ. Рабочие заказы и физические
остатки сохранены: 8 заказов, 79 товаров, 307 фотографий, 0 резервов.
Очередь и failed jobs пусты. Финальные проверки подтвердили свежие heartbeat
и отсутствие оставшихся диагностических заказов.
