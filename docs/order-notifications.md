# Уведомления о заказах и обратных звонках

Заказ (или заявка на звонок) и записи `order_notifications` сохраняются в одной
транзакции. Каждому менеджеру и покупателю соответствует отдельная запись и
отдельное задание `SendOrderNotification`. Ошибка постановки задания не меняет
успешный ответ покупателю и не препятствует постановке остальных уведомлений.

## Настройки

В production необходим реальный почтовый транспорт и работающий обработчик
очереди. Пример переменных без учётных данных:

```dotenv
QUEUE_CONNECTION=database
DB_QUEUE_RETRY_AFTER=120
MAIL_MAILER=smtp
MAIL_TIMEOUT=20
ORDER_NOTIFICATION_EMAILS=manager1@example.com,manager2@example.com
```

SMTP-хост, порт, TLS, учётные данные и `MAIL_FROM_ADDRESS` настраиваются отдельно
под выбранного провайдера. Пустой `ORDER_NOTIFICATION_EMAILS` использует прежний
`ORDER_NOTIFICATION_EMAIL`, а при его отсутствии — `MAIL_FROM_ADDRESS`.
Адреса обрезаются по краям, приводятся к нижнему регистру и дедуплицируются.
Некорректный или пустой список менеджеров отклоняется до фиксации заказа.
Менеджеры получают отдельные письма и не видят адреса остальных получателей.

`sync` поддерживается для разработки, но отправляет письма в HTTP-запросе и
не обеспечивает повторы worker. `log` и `array` не доставляют письма адресатам;
`sent_at` с ними означает только успешное выполнение этого транспорта.
Также не следует использовать `failover` с резервным транспортом `log` для
production: ошибка SMTP тогда может считаться успешной отправкой.

## Яндекс Почта autobagaz@yandex.ru

Локальные `.env` и `.env.example` подготовлены для отправки через этот ящик:

```dotenv
MAIL_MAILER=smtp
MAIL_SCHEME=smtps
MAIL_HOST=smtp.yandex.ru
MAIL_PORT=465
MAIL_USERNAME=autobagaz
MAIL_PASSWORD=
MAIL_FROM_ADDRESS=autobagaz@yandex.ru
MAIL_FROM_NAME="Автобагаж"
MAIL_TIMEOUT=20
ORDER_NOTIFICATION_EMAILS=autobagaz@yandex.ru
```

Этот же ящик выбран получателем уведомлений менеджера. Для другого получателя
изменить `ORDER_NOTIFICATION_EMAILS`. Если задан `MAIL_URL`, удалить его или
задать `null`, чтобы он не переопределял эти параметры.

В настройках Яндекс Почты «Почтовые программы» разрешить доступ почтовых
клиентов по IMAP и использование паролей приложений. В Яндекс ID создать
отдельный пароль приложения типа «Почта», например с именем «Сайт Автобагаж»,
и вписать его в `MAIL_PASSWORD` в закрытом `.env`. Пароль аккаунта не использовать.
Для адреса на `yandex.ru` в качестве логина указан `autobagaz`.

Источник: [инструкция Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others).

Скрипт публикации не загружает `.env` и `.env.example`. При выкладке нужно отдельно
перенести указанные параметры в существующий серверный `.env` и пересобрать
кеш конфигурации. Не заменять серверный `.env` целиком локальным: в нём другие
параметры БД, приложения и окружения. Для отправителя на `yandex.ru` почтовые
DNS-записи обслуживает Яндекс; менять SPF/DKIM домена сайта для этой отправки
не требуется.

## Повторы и восстановление

У задания пять попыток, интервалы между ними — 60, 300, 900 и 3600 секунд.
Таймаут задания — 60 секунд; SMTP по умолчанию — 20 секунд. `retry_after`
подключения очереди должен превышать таймаут задания. Для database и Redis
значение по умолчанию — 120 секунд. Ограничения CLI PHP и хостинга проверяются
при настройке сервера.

Не поставленные в очередь уведомления восстанавливает команда:

```bash
php artisan orders:dispatch-notifications --limit=100
```

Она зарегистрирована в Laravel Scheduler каждую минуту с защитой от
перекрывающихся запусков. На сервере потребуется запуск `schedule:run` и worker.
Команда возвращает ненулевой код, если после прохода остались ожидающие
постановки записи (в том числе из-за ограничения `--limit`).

Задание блокирует запись на время отправки, а после принятия письма транспортом
заполняет `sent_at`. Повторно обработанное задание для отправленной записи
ничего не отправляет. Сбой постановки оставляет запись ожидающей; ошибка
доставки передаётся worker для повторов. После исчерпания попыток заполняется
`failed_at`, а worker сохраняет задание в `failed_jobs` при включённом
`QUEUE_FAILED_DRIVER=database-uuids`.

После устранения причины:

```bash
php artisan queue:failed
php artisan queue:retry UUID
```

Повторное успешное выполнение очищает `failed_at`. Автоматическое восстановление
не ставит уже поставленные задания повторно: они принадлежат очереди, включая
`failed_jobs`. Не удаляйте задания очереди, рассчитывая на их автоматическое
восстановление. Старые заказы, созданные до этой миграции, не получают уведомления
задним числом.

При обрыве процесса после принятия SMTP письма, но до записи `sent_at` возможен
дубль. Та же неопределённость есть при использовании внешнего брокера вместо
очереди в основной БД: брокер мог принять задание до отката локальной транзакции.
Гарантии однократной доставки SMTP не предоставляет. Длительная отправка держит
транзакцию открытой; для небольшого потока уведомлений используйте один worker.

## Наблюдение

```bash
php artisan orders:notification-status --max-age=15
```

Команда выводит JSON со счётчиками ожидающих постановки, поставленных,
окончательно неудачных и задержанных уведомлений, а также всех `failed_jobs`.
Ненулевой код означает наличие окончательных ошибок или уведомлений старше
порога. При другом драйвере failed jobs поле `failed_jobs` равно `null`.
Эту проверку нужно подключить к серверному мониторингу с независимым каналом
оповещения. Записи журнала содержат ID уведомления и класс исключения,
без адресов, содержимого письма и SMTP-реквизитов.

## Выкладка

Применить миграции до открытия приложения для запросов, пересобрать кеш
конфигурации и перезапустить постоянный worker. Перед первой выкладкой проверить,
что выбрана очередь с сохранением заданий, а не `null`, `deferred` или
`background`. Серверная настройка и проверка реальной доставки выполняются отдельно.
