# Публикация на new.autobagaz.ru по SFTP

Для повторных публикаций используется скрипт:

```bash
scripts/deploy-sftp.sh
```

Он выполняет production-сборку, Pint и PHPUnit, сравнивает локальные файлы с
SHA-256-манифестом на сервере, сохраняет резервную копию заменяемых файлов,
загружает только изменения по SFTP, удаляет только отсутствующие локально файлы
из предыдущего манифеста, запускает миграции и пересобирает кеши
Laravel. Временный PHP-файл запуска создаётся со случайным именем и удаляется
сразу после выполнения.

Перед удалением таблицы `vehicle_body_types` скрипт автоматически сохраняет
её записи и связи с конфигурациями в `storage/app/deploy/backups` на сервере.

Пароль в проекте не хранится. Скрипт использует переменную
`JINO_SFTP_PASSWORD` или сохранённый профиль Jino в FileZilla:

```text
~/.config/filezilla/sitemanager.xml
```

## Обычная публикация

Сначала посмотреть список файлов:

```bash
scripts/deploy-sftp.sh --dry-run
```

Затем опубликовать:

```bash
scripts/deploy-sftp.sh
```

## Первый запуск

Если текущая копия уже вручную синхронизирована с сервером, создать исходный
манифест без загрузки файлов:

```bash
scripts/deploy-sftp.sh --initialize
```

Если состояние сервера неизвестно, выполнить полную загрузку:

```bash
scripts/deploy-sftp.sh --full
```

## Обновление зависимостей

Скрипт публикует composer.lock, но **не устанавливает зависимости Composer
и не загружает vendor**. Изменение lock-файла само по себе не обновляет
серверные библиотеки. При изменении PHP-зависимостей отдельно подготовьте
production-vendor из lock-файла с --no-dev и оптимизированным автозагрузчиком,
сохраните прежний vendor и проверьте установленные версии после замены.
Не запускайте composer update на сервере.

Порядок и результаты отдельной публикации зависимостей 22 октября описаны в
[отчёте о выпуске](releases/2026-10-22-security-dependencies.md).
Обновление самого интерпретатора PHP выполняется средствами хостинга.

## Дополнительные параметры

- `--skip-checks` — пропустить сборку и тесты;
- `--dry-run` — ничего не изменять на сервере;
- `--full` — загрузить все разрешённые файлы;
- `--initialize` — только записать исходный манифест.

Локальные резервные копии сохраняются в игнорируемой Git папке:

```text
.codex/deploy/backups/
```

Скрипт никогда не загружает `.env`, локальную базу, `storage`, `public/storage`
или пользовательские файлы. Удаление ограничено файлами из предыдущего
deploy-манифеста и разрешёнными каталогами приложения; перед удалением файлы
скачиваются в локальную резервную копию.

## Полные копии данных на локальном компьютере

Полная копия отличается от копии заменённых файлов публикации:

```bash
python3 scripts/backup-sftp.py
```

Используется тот же профиль FileZilla или `JINO_SFTP_PASSWORD`, проверка ключа
хоста обязательна. SSH-команды на текущем хостинге недоступны. Скрипт загружает
временный PHP-обработчик со случайным именем и отдельным Bearer-токеном; после
авторизации обработчик удаляет себя. Не публикуйте `scripts/backup-data.php`
вручную в `public`. Выгрузка не меняет записи в рабочей БД.

Копии находятся вне репозитория:

```text
/home/igoldyrev/.local/share/autobagaz/backups/<UTC-дата-время>-<идентификатор>/
```

Другой каталог задаётся через `AUTOBAGAZ_BACKUP_DIR`. Доступ к каталогу имеет
текущий пользователь ОС (700, файлы 600); пароли в Git не сохраняются.
Архив **не зашифрован**: он содержит персональные данные, пароли подключений
и `APP_KEY`. Для переноса в облако потребуется шифрование и отдельное хранение
ключа. Сейчас копии находятся только на этом компьютере и не защищают от его
потери. Для восстановления нужны доступ к этой учётной записи ОС и каталогу
копий; для новой выгрузки — также профиль SFTP с паролем и доверенным ключом
сервера в `~/.ssh/known_hosts`.

Комплект содержит:

- `database.sql.gz` — схема и все строки MySQL, включая очередь и failed jobs;
- `data.ndjson.gz` — переносимый экспорт всех таблиц для локальной SQLite;
- `site.zip` — версия серверного приложения, vendor, public, пользовательские
  файлы из `storage/app/public` и `storage/app/private`, `.env` с исходным ключом;
- `manifest.json` — количества записей, размеры и SHA-256 файлов;
- `restore-check.json` — результат отдельной проверки восстановления, если она выполнена.
- `mysql-restore-check.json` и `recovery-exercise.json` — результаты проверки SQL
  и команд восстановления на отдельном экземпляре БД/приложения, если она выполнена.

MySQL выгружается в согласованной read-only транзакции InnoDB. Таблицы другого
типа, views, triggers, routines и events приводят к отказу: этот скрипт их не
экспортирует. Параллельные публикации и изменения схемы во время копирования
недопустимы. Файлы проверяются по SHA-256, но общая атомарная точка БД и файлов
без остановки записей не гарантируется. Для снимка перед разрушительной
миграцией остановите записи и фоновые задачи по порядку ниже.

Логи, кеши Laravel, старые серверные копии и символьная ссылка `public/storage`
не входят в комплект. Ссылка и кеши создаются заново. SQL восстанавливает
таблицы приложения; права и учётную запись MySQL нужно создать отдельно.

Каталоги `.partial` не считаются готовыми копиями. После сверки контрольных
сумм каталог переименовывается, временный комплект на сервере удаляется.
При сбое на сервере могут остаться файлы в
`storage/app/deploy/data-<идентификатор>` вне public: проверяйте их перед ручной
очисткой. Не удаляйте последнюю исправную локальную копию.

После успешного копирования сохраняются последние 14 дневных, 8 недельных и
6 месячных снимков (для каждого периода — последний). При свободном месте
меньше 1 ГиБ запуск завершается ошибкой. Контроль места нужен и на хостинге:
на время выгрузки там создаётся полный архив.

На этом компьютере ежедневный запуск обслуживает пользовательский systemd timer
`autobagaz-backup.timer`, время 04:00 Asia/Yekaterinburg с задержкой до 10 минут.
При пропущенном запуске таймер выполняет копирование после следующего старта
пользовательского менеджера systemd. Выключенный компьютер копии не создаёт;
потеря новых данных может превысить сутки. Автоматическая выгрузка **не заменяет
локальные данные сайта**.

```bash
systemctl --user status autobagaz-backup.timer
systemctl --user list-timers autobagaz-backup.timer
journalctl --user -u autobagaz-backup.service -n 50
```

## Проверка восстановления и синхронизация локального сайта

Сначала проверить выбранную полную копию, не меняя рабочую локальную БД:

```bash
python3 scripts/restore-local.py /полный/путь/к/копии
```

Создаётся отдельная SQLite, схема строится существующими миграциями проекта,
затем переносятся все таблицы. Проверяются состав таблиц/колонок, количества
записей, SQLite integrity check, внешние ключи, контрольные суммы архива и
наличие загруженных изображений, на которые ссылаются данные. Несовпадение
схемы прерывает процесс до замены локальных данных.

Для синхронизации остановите локальные worker/scheduler и сайт, затем выполните:

```bash
python3 scripts/restore-local.py /полный/путь/к/копии --activate
php artisan serve --host=127.0.0.1 --port=8000
```

Прежние `.env`, SQLite и `storage/app/public` сохраняются в
`.codex/data-backup/local-before-sync/<UTC-дата-время>/`. В локальном `.env`
сохраняется свой `APP_KEY`, выбирается SQLite, письма переводятся в `log`,
токен и адресаты Telegram отключаются, сессии сохраняются в файлы.
Серверный `.env` не активируется. Таблицы очереди переносятся как данные;
не запускайте их обработку на локальной копии без отдельной проверки.
Код и vendor локального проекта не заменяются серверными файлами.

При необходимости вернуть прежнее локальное состояние: остановить сайт,
вернуть `.env`, `database.sqlite` и каталог `public` из выбранного
`local-before-sync` на их исходные места, выполнить `php artisan optimize:clear`.
Перед заменой SQLite не должно оставаться активных соединений и WAL-файлов.

## Остановка фоновых задач и откат на хостинге

На текущем Jino worker и scheduler запускаются каждую минуту через cron;
точные команды приведены в [инструкции уведомлений](order-notifications.md).
Постоянного scheduler-процесса здесь нет, worker запускается с
`--stop-when-empty --max-time=50`. Лимит проверяется между заданиями: дождитесь
завершения текущего задания, а не просто истечения 50 секунд.

Порядок для публикации с изменением данных или восстановления:

1. Сохранить текущий комплект приложения и данных. Для согласованного снимка
   закрыть приём записей (`artisan down` через доступный защищённый механизм
   запуска PHP), отключить **обе** задачи cron в панели Jino и дождаться
   завершения текущего worker и `schedule:run`. Maintenance сам по себе
   не останавливает все фоновые задачи. Не использовать `--force` у worker.
2. Получить полный снимок и проверить его. Не начинать необратимые изменения
   при отсутствии исправной копии. Сохранить версию до публикации, а не после неё.
3. Для отката приложения вернуть соответствующий комплект исходников,
   `composer.lock`, vendor, `public/build` и остальных ресурсов. Обычная копия
   изменённых файлов публикации может не содержать vendor. Учесть добавленные
   неудачной публикацией файлы и восстановить deploy-манифест либо сформировать
   его заново только после сверки фактических файлов.
4. Если требуется откат БД, сначала восстановить SQL в **отдельную пустую MySQL
   БД** с совместимой версией сервера и сравнить данные. Дамп содержит
   `DROP TABLE`, его нельзя направлять в действующую БД для пробной проверки.
   Пример импорта с реквизитами в защищённом конфигурационном файле:

   ```bash
   set -o pipefail
   gzip -dc /путь/к/копии/database.sql.gz | mariadb --defaults-extra-file=/защищённый/restore.cnf --database=отдельная_бд
   ```

   Проверить код завершения импорта, состав таблиц, все строки и внешние ключи.
   Простое `SET FOREIGN_KEY_CHECKS=1` не проверяет уже загруженные записи.
   Для отдельной локальной БД с аутентификацией через Unix socket есть проверка:

   ```bash
   php scripts/verify-mysql-backup.php /путь/к/копии /путь/к/mysql.sock отдельная_бд пользователь
   ```

   Она работает только на чтение, проверяет SHA-256 трёх архивов, сравнивает
   каждое значение каждой строки SQL-БД с независимым `data.ndjson.gz` и ищет
   нарушенные внешние ключи, включая составные. Пароль этот локальный
   проверочный скрипт не принимает; для хостинга требуется адаптированный
   защищённый способ подключения, без публикации реквизитов.

   Затем, в закрытом для записи приложении, переключить подключение на проверенную
   БД и восстановить пользовательские файлы из того же комплекта. Сохранить
   исходный серверный `APP_KEY`. Возврат старой БД теряет заказы и изменения после
   снимка; сначала сохранить аварийное текущее состояние и решить, как перенести
   новые записи. `migrate:rollback` не заменяет восстановление удалённых данных.
5. Под восстановленную версию приложения пересобрать кеши:
   `package:discover`, `config:cache`, `route:cache`, `view:cache`.
   Каталоги `storage/framework/{cache/data,sessions,views}` и `bootstrap/cache`
   должны существовать и быть доступны PHP на запись. Выполнить `storage:link`.
   Проверить `migrate:status`; не запускать новые миграции автоматически при откате.
6. Проверить `queue:failed` и `orders:notification-status --max-age=15`.
   Не очищать `jobs`, `failed_jobs` или `order_notifications`: уже поставленные
   задания автоматически повторно не создаются. После устранения причины
   повторять только выбранные задания через `queue:retry UUID`. Для уведомлений,
   ещё не поставленных в очередь, использовать `orders:dispatch-notifications`;
   повторять проход при превышении `--limit`.
7. Выполнить `queue:restart` с тем же кешем, который использует worker. Включить
   обе исходные cron-задачи, снять maintenance через `up`. Здесь следующий cron
   сам запустит worker с новым кодом; `queue:restart` сам процесс не запускает.
   Проверить журнал worker, отметку scheduler, отсутствие роста очереди и
   защищённый monitoring snapshot. Проверить главную, каталог, изображение и
   вход администратора.

После отката старой БД уведомления с `sent_at` после момента снимка могут
отправиться повторно. Перед включением worker сверить уже выполненные отправки;
SMTP не гарантирует однократную доставку. Подробности и повторы описаны в
[существующей инструкции](order-notifications.md#повторы-и-восстановление).
